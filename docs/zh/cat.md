# `fastx cat`：设计与实现原理

对应源码：`src/fastx/cat.rs`、`src/common/hash.rs`。

## 动机

把同一个生物样本在多个 lane/flowcell 上测的原始 FASTQ 直接拼接起来（多次测序
凑覆盖度）是行业标准做法，正常情况下是安全的——真实的 Illumina read ID 里带
flowcell/lane/tile/坐标信息，实际场景里不同批次之间基本不会撞 ID。真正会出问题
的不是 ID 命名机制本身，而是操作失误：同一个文件被误加进文件列表两次（路径写
重了、复制粘贴的 glob 匹配到了不该匹配的东西）。普通的 `cat` 对这种错误完全
没有任何察觉能力——悄悄拉高覆盖度、把重复数据混进下游比对/变异检测，产出的
文件本身看不出任何异常。`fastx cat` 干的事情跟 `cat` 一样，但在流式处理的过程
中专门检查这一点，一旦发现重复 ID，立刻带着具体是哪个源文件、哪个位置报错
中止。

## 流式查重

每个源文件流式读取的过程中，每条记录的 `FastqRecord::base_id()` 都会被哈希
（`common::hash::fnv1a`，跟 `fastx deinterleave` 做布局检测用的是同一个函数
——为什么用哈希而不是完整字符串见 `docs/zh/interleave.md`），然后去一个正在
维护的 `HashMap<u64, (PathBuf, u64)>` 里查——这个表以哈希值为 key，存着这个
ID 第一次出现时所在的源文件和局部记录序号。同一个哈希第二次出现会立刻报错：

```
duplicate read ID "...": first seen in run1_R1.fq.gz (record #412),
again in run1_R1.fq.gz (record #412) -- did you accidentally include
the same file twice?
```

这是在流式处理**过程中**触发的，不是事后才发现——出问题的点之后没有任何有意义
的输出需要调用方回头清理，报错信息里的具体文件/位置正是排查文件列表哪里写错了
所需要的信息。`--allow-duplicate-ids` 可以在这个检查是误报的场景下关掉（比如
某个平台本来就不保证全局唯一 ID）。

## 双端模式一次检查两件事

双端模式下（传了 `--r2`），每个源文件对都通过 `spawn_reader`/`recv_pair_step`
并发读取——跟 `fastx sample`/`fastx rescue`/`fastx interleave` 是同一套机制
——这意味着 `fastx cat` 顺带免费拿到了第二项独立检查：每个源文件对**内部**
的 R1/R2 配对是否正确。如果某一次测序的两个 mate 文件本身就错位了（条数不
一样，或者 ID 对不上），会在数据被拼进最终结果之前就被发现并报错，而不是混进
最终产出，变成一个下游才暴露、而且很难倒查回"五个输入文件里到底是哪一个有
问题"的失败。

## 多个来源，顺序完全显式

输入通过重复的 `--r1`/`--r2` 参数给出，而不是逗号分隔列表或者目录通配符，所以
拼接顺序永远精确对应命令行上写的顺序，不用去操心不同平台下 glob 展开顺序可能
不一致的问题：

```
genorush fastx cat --r1 run1_R1.fq.gz --r1 run2_R1.fq.gz \
                    --r2 run1_R2.fq.gz --r2 run2_R2.fq.gz \
                    -o merged_R1.fq.gz -O merged_R2.fq.gz
```

`--r1`/`--r2` 必须传相同次数，且顺序一一对应（第 `i` 个来源的 R1 是 `--r1`
第 `i` 次出现的值，R2 是 `--r2` 第 `i` 次出现的值）。单端模式只传 `--r1`，
不传 `-O`/`--out2`。

## 已验证的行为

用两份构造出来的、各 500 对的"测序批次"数据（用不同的 read ID 前缀模拟真实
不同批次）测试过：正常合并两个批次成功产出 1000 对，顺序跟源文件顺序一致，
内容和 R1/R2 配对都验证跟预期结果逐字节一致/零错位。故意把同一个源文件传两遍
会被立刻抓到，报错信息里带着具体的文件名和记录位置；`--allow-duplicate-ids`
验证过能精确关掉这一项检查，同时依然正确处理（现在翻倍了的）输入内容。
