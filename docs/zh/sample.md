# `fastx sample`：设计与实现原理

对应源码：`src/fastx/sample.rs`、`src/common/fastq.rs`、`src/common/rng.rs`。

## 动机

`seqkit sample` 是这个命令参考的对象，本命令刻意改进了它一个明确的短板：
**它没有"双端"这个概念**。要对 Illumina R1/R2 做下采样，只能对两个 mate 文件
各跑一遍，靠两次都传**完全相同**的 `-s/--rand-seed`，让两次完全独立的调用"恰好"
在每个 read 序号上做出相同的取舍决策。`genorush fastx sample` 则是在同一个
进程里同时读两个 mate 文件，每一个 read *对*只做一次决策——配对正确性是算法本身
的性质，而不是依赖调用者每次都正确遵守的一个约定。

## 先读懂 `seqkit sample` 的真实算法

在设计对照方案之前，直接读了它的源码（`shenwei356/seqkit` 仓库的
`seqkit/cmd/sample.go`），而不是凭 CLI 文档猜测。两种模式：

- **`-p`（按比例）**：单遍扫描；每条记录都从一个带种子的 `math/rand.Rand`
  里取一次 `rand.Float64()`，取值 `<= p` 就保留。每条记录消耗一次随机数抽取，
  按文件顺序，来自同一个顺序推进的生成器。
- **`-n`（按条数）**：要么把**全部**记录读进内存（`fastx.GetSeqs`），然后用
  `proportion = n/总数 * 1.1` 做同样的伯努利试验，凑够 `n` 条就停；要么加
  `--two-pass`，先读一遍文件只为了数出总数（`fastx.GetSeqNumber`），再读第二遍
  应用同样的"放大比例"技巧。不管哪种方式，本质上都是"近似再截断"的方案，不是
  精确的单遍抽样算法；`--two-pass` 存在的唯一目的是避免整份读进内存，代价是
  把文件读两遍。

因为 `-p` 模式严格按文件顺序、每条记录只消耗一次随机数，所以只要两个文件条数
相同、顺序一致，用相同种子跑两遍确实**能**得到一致的配对——两条随机数流逐次
完全相同，第 i 次决策在两次运行里也相同，包括 `-n` 模式里循环提前 break 的情况
（因为两次运行会在同一个 read 序号上凑够目标条数）。在这些前提条件成立时，这套
方案本身是对的；本命令要弥补的是**操作层面**的缺口——两次调用、两次完整读文件、
没有任何跨文件校验、种子得手动敲两遍还必须完全一致、`-n` 场景下种子万一敲差了
或者两个文件条数不一致时完全没有任何提示。

## 不只是接口变了，两处核心算法也换掉了

### 1. 比例抽样：一个无状态、可并行的决策函数

Go 的 `math/rand.Rand` 天生是顺序的——第 N 次调用会把生成器推进到第 N+1 次
调用的状态。`common::rng::deterministic_f64(seed, index)` 换成了一个纯函数：
把种子和记录的全局序号一起丢进 SplitMix64 的混合函数
（`z ^= z>>30; z *= C1; z ^= z>>27; z *= C2; z ^= z>>31`，和
`java.util.SplittableRandom`、Rust 自家 `rand` crate 内部用的是同一套
finalizer），得到一个只依赖 `(seed, index)` 本身的值——算第 5,000,000 次抽取
根本不需要先算完第 1 到 4,999,999 次。这正是能把记录分批交给
`rayon::par_iter()` 并行处理的前提：每条记录的取舍决策跟哪个线程算它、按什么
顺序算都没关系，不管 `--chunk-records` 怎么调、开多少线程，结果都完全一致——
这个性质本身也直接写了单元测试去验证（`common::rng::tests`）。在双端模式下这个
设计是"免费"复用的：第 `i` 次抽取直接决定第 `i` 对（只抽一次，不是两次），
所以两个 mate 之间根本不存在"决策不一致"这种可能性。

### 2. 精确条数抽样：单遍水库抽样（Algorithm R）

`seqkit sample -n` 要么把整个输入放进内存，要么把文件读两遍。其实这两个都不
必要：**水库抽样（reservoir sampling）** 正是用来解决"从一个长度未知的流里
均匀随机选出恰好 k 个元素"这个问题的，单遍扫描、`O(k)` 内存，仅此而已——不需要
事先知道总数，也不需要读第二遍。经典算法（Vitter 的 "Algorithm R"），直接实现
在 `run_reservoir_se`/`run_reservoir_pe` 里：

```text
for i, item in enumerate(流):
    if i < k:
        reservoir[i] = item
    else:
        j = uniform_random(0, i)   # 含 i
        if j < k:
            reservoir[j] = item
```

等整条长度为 `n` 的流处理完之后，每个元素落进水库的概率恰好都是 `k/n`——这是
一个标准的、可以用归纳法证明的经典结论（这里不是发明了新算法，只是把它用在了
`seqkit` 没有用到的地方）。`common::rng::SplitMix64::next_below(bound)` 用
Lemire 的近乎无除法的无偏方法提供 `[0, bound)` 区间内的均匀抽取，避免了朴素的
`rng() % bound` 会引入的小幅取模偏差。

双端模式下，水库里存的是 `(原始序号, R1记录, R2记录)` 三元组——一对读长作为
一个整体被保留或替换，精确性和配对正确性都是这一份数据结构自然带来的结果。每个
被保留的元素还记着自己在原始流里的位置，所以扫描结束后会按这个位置重新排序
（`chosen.sort_by_key(|(idx, ..)| *idx)`）再写出——水库抽样过程中元素被替换的
顺序不是原始顺序，重新排回原始顺序只是一次很便宜的 `O(k log k)` 排序，纯粹是
为了输出的可读性/确定性，不影响正确性。

这也意味着 `-n` 完全不需要 `--two-pass` 这种选项：Algorithm R **本来就**
把内存限定在抽样目标数量上，单遍扫描，跟输入大小无关。（相比之下 `seqkit` 里
`--two-pass` 是用户必须主动权衡取舍的一个真实选项。）

## 双端并发读取

`spawn_reader()` 把每个输入文件的解压 + FASTQ 解析都放在各自独立的操作系统
线程里，解析出来的 `FastqRecord` 通过一个有界的 `std::sync::mpsc::sync_channel`
流式发给主线程。单端模式下这主要是让 I/O 和（很轻量的）抽样决策的耗时可以重叠。
双端模式下差别更明显：不是像跑两次 `seqkit sample` 那样先解压 R1 再解压 R2，
而是两个文件在各自线程上**同时**解压——gzip 解压是 CPU 密集型工作，所以在多核
机器上这是实打实的墙钟时间收益，跟 `-j` 给 rayon 分配了多少线程去做比例抽样的
批处理是两码事。

## 配对正确性，做成了结构性保证

`recv_pair()`（`src/fastx/sample.rs`）每一步都从两个 mate 各自的 channel 里
取一条记录，在任何抽样决策发生之前先强制两条不变量：

1. **同步 EOF**。如果一个 channel 先于另一个关闭，直接报错
   （`read 1/2 have different numbers of reads`）——`seqkit` 那种跑两遍的方式
   完全没有能力检测到这种情况；每次调用都只看得到自己那一个文件。
2. **ID 对应关系**（除非传了 `--no-pair-check`）。`FastqRecord::base_id()`
   去掉开头的 `@`，取第一个以空白分隔的 token，再去掉结尾的 `/1` 或 `/2`——
   同时兼容老式 Illumina header（`@READ/1`、`@READ/2`）和现代 header
   （`@READ 1:N:0:...`、`@READ 2:N:0:...`）。任意位置出现不匹配都会立刻中止，
   报出具体的 pair 序号和两边的 ID，而不是悄悄产出一份错位的配对结果。

这两项检查都专门做了测试：故意截短 R2（少一条记录）能在两条流真正出现分歧的
那个 pair 序号上被抓到；人为整体错位的 R2（header 对不上了）在 pair `#0` 就被
抓到；`--no-pair-check` 能正确地只关掉 ID 检查，条数不一致的检查依然照常触发。

## 命令形态

```
genorush fastx sample -i reads.fq.gz -p 0.1 -o sub.fq.gz -s 42
genorush fastx sample -i reads.fq.gz -n 50000 -o sub.fq.gz -s 42
genorush fastx sample -i R1.fq.gz -I R2.fq.gz -o R1.sub.fq.gz -O R2.sub.fq.gz -p 0.1 -s 42
```

参数命名（`-i/--in1`、`-I/--in2`、`-o/--out1`、`-O/--out2`）刻意贴的是
`fastp` 的风格而不是 `seqkit` 的，因为这个领域大部分用户对双端 I/O 参数命名的
肌肉记忆来自 `fastp`。`-p`/`-n` 用 `clap` 的 `conflicts_with` 做互斥；"两者
必须传一个"这条规则是在 `run()` 里手动检查的，没有用 `clap` 的 `ArgGroup`——
因为两者都是没有默认值的 `Option<T>`，手动检查反而更直观。`-r/--non-deterministic`
故意没有对 `-s/--seed` 设置 `conflicts_with`——`-s` 带了 `default_value_t`，
clap 会把它当成"始终存在"，如果设置 `conflicts_with`，光传一个 `-r`（最常见的
用法）就会被误判为冲突；两者的优先级（都传时 `-r` 生效）是在 `effective_seed()`
里手动解决的。

## 已验证的行为

用 20 万对 150bp 的模拟双端 read、以及 2 万条 500–3000bp 变长的模拟长读长
（单端）做了测试：比例抽样结果落在目标值附近合理的抽样噪声范围内（`-p 0.1`
实测约 9.75%，符合预期）；`-n` 水库抽样返回的条数**精确**等于要求的数量；双端
比例抽样产出的 R1/R2 条数完全一致，全部输出里 ID 零错位；gzip 输入输出往返
正常；构造出来的格式错误/错位双端输入会被拦截，报出明确具体的错误信息，进程
退出码为 1。`common::rng` 和 `common::fastq`——这两个模块很可能会被以后所有
面向"记录"的命令复用——都配了覆盖确定性、均匀性、FASTQ 结构校验边界情况的
单元测试。
