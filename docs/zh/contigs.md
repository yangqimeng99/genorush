# `check contigs`：设计与实现原理

对应源码：`src/check/contigs.rs`、`src/common/contigs.rs`。

## 动机

一个比对到 `1, 2, 3` 命名参考的 BAM，和一个注释到 `chr1, chr2, chr3` 命名参考的
VCF，**两个文件都完全合法**，本身都没有错。把它们放在一起用的工具通常也不会
崩——它只是在匹配不上的 contig 上什么都找不到，然后把"找不到"报成 0，而这和
真实结果长得一模一样。

长度不一致更糟。同一套组装的两个 build 可能在某条染色体上只差几个碱基，从那个
位置往后所有坐标都偏了这么多，而没有任何东西会说出来。GATK 偶尔会以
"incompatible contigs" 报出这一类，常规解法是绕一趟 Picard。这个命令把这项检查
单独提前做掉。

它同时也是这个项目格式读取层的起点，所以它的另一个职责是：**证明那一层在生态
真实产出的文件上能用**。

## 什么算不一致

第一个文件是基准，其余都与它比对。这个不对称是有意的，因为两个方向含义不同：

- **基准里没有的 contig**：致命。任何同时消费两个文件的工具都会在那里静默地
  什么也找不到。信息里会在能判断时指出命名约定——`chr1 -- the reference calls
  it "1"` 把"找不到"变成"怎么改"，而 `chr` 前缀和 `MT`/`chrM` 的写法差异占了
  这类问题的绝大多数
- **长度不同**：致命，并且直接说明它是什么——两个不同的基因组 build
- **顺序不同**：只是提示。它对"要求按固定字典序排序输入"的工具有意义，对多数
  工具无所谓，所以由 `--require-order` 把它提升为失败，而不是默认就失败
- **基准有、而该文件没提到的 contig**：正常——一个 BED 只会列出它覆盖到的部分
  ——所以只计数、不标记。但如果这个文件**同时**用了基准没有的名字，那它就不是
  "覆盖了一部分"，而是同一个命名问题的另一面，这时再说"正常"就是误导

## 从九种格式里读出 contig

`common::contigs` 把所有支持的格式归一成同一个形状：一个名字，以及在有声明时的
长度。但各格式的工作量差别极大，处理方式也因此不同：

| 格式 | 信息来源 | 读取方式 |
|---|---|---|
| `.fai`、`.chrom.sizes`、`.genome` | 前两列 | 自己读 |
| FASTA | 优先读同名 `.fai`，否则完整扫一遍 | 自己读 |
| VCF | `##contig` 头部行 | `noodles-vcf` |
| BCF | 同上，在二进制头里 | `noodles-bcf` |
| SAM | `@SQ` 记录 | `noodles-sam` |
| BAM | 同上，在二进制头里 | `noodles-bam` |
| CRAM | 同上，在 file header 容器里 | `noodles-cram` |
| GFF/GTF | `##sequence-region` 指令，否则取第一列 | 自己读 |
| BED | 第一列 | 自己读 |

这个分界是刻意的。VCF、BCF、SAM、BAM、CRAM 的头部是**真正的解析问题**，其中三个
还是带自有压缩框架的二进制格式——那正是该用库的地方，`noodles` 也由此进入这个
项目。而 GFF 的 contig 名字不过是制表符分隔行的第一个字段，为了
`split('\t').next()` 引入一个会随版本变化的解析器，是只有成本没有收益的。等到
某个命令需要真正**操作** GFF 而不只是瞥一眼时，再加也不迟。

有两个细节很容易踩错：

- **BCF、BAM、CRAM 要按文件直接打开**，而不走这里所有文本格式共用的那个"嗅探
  gzip"的 reader。它们自带压缩框架，把一个已经解压过的流交给一个准备自己解压的
  reader，什么也读不出来
- **CRAM 的 `read_header` 要求流位于最开始**。它自己会校验 magic number 并跳过
  file definition，所以先调用旁边那个 `read_file_definition`（名字很有诱惑力）
  反而会让它读到错误的位置，然后报 invalid header

FASTA 在存在同名 `.fai` 时优先读索引——索引本来就是干这个的，这能把"完整扫一遍
几十亿碱基"变成"读几 KB"。

## 已验证的行为

`tests/check_contigs.rs` 用的 fixture 是**参考实现产出的**、不是手写的——
`samtools view -b`、`samtools view -C`、`bcftools view -Ob`、`samtools faidx`
——因为这些测试的意义就在于"读得了真实的 BAM/CRAM/BCF"，而一个照着读取器编造
出来的 fixture 恰恰证明不了这件事。来源记录在
`tests/data/contigs/README.md`。

覆盖：每种格式都被读出正确的 contig 数与长度；`chr` 前缀不一致会失败并给出命名
提示、且**不会**同时被描述成"覆盖了一部分"；长度不一致会失败并说明原因；顺序
不同在 `--require-order` 之前只是提示；部分覆盖只是提示；无法识别的扩展名会列出
支持的清单。
