# `fastx rescue`：设计与实现原理

对应源码：`src/fastx/rescue.rs`，以及 `src/common/fastq.rs` 里的共享基础设施
（`spawn_reader`、`PairStep`、`recv_pair_step`）。

## 动机

一个很常见的现实场景：FASTQ 下载（不管是单端长读长，还是 Illumina 的 R1/R2
双端）在中途断了，留下一个 gzip 流被截断、或者末尾校验和不对的 `.fq.gz`。这个
文件并不是完全没用的垃圾——截断点**之前**解压出来的所有内容都是完好的测序数据；
对双端数据来说，只要某一对里两个 mate 都被完整、正确地解压出来了，这一对就依然
能用来做比对。整个文件直接扔掉，等于白白丢弃了真实存在、重新获取代价很高的数据。
`fastx rescue` 做的事情就是精确地找出那段"从头开始、完全干净、格式正确"的记录
（或者 read 对），把它们写出来，一旦发现问题就干净地停下，而不是直接报错退出。

## 复用 `fastx sample` 的读取基础设施，但错误处理策略完全相反

`fastx sample` 之前已经解决过"并发读取两个 mate 文件、检测它们是否错位"这个
问题（见 `docs/zh/sample.md`）。`rescue` 需要的机制一模一样——但 `sample`
把错位当成致命错误处理（必须中止，因为从错位的配对里抽样会悄悄产出错误的结果），
`rescue` 存在的意义恰恰是"尽量往后读，读到哪算哪，遇到问题就优雅地停下"。与其
把读取/配对逻辑复制一份、把错误处理方向反过来重写一遍，不如把共享的部分单独
提出来放进 `common::fastq`：

- **`spawn_reader(path) -> Receiver<Result<FastqRecord>>`**：在独立的操作系统
  线程上解压并解析一个文件，把记录通过一个有界 channel 流式发出去。遇到
  读取/解析错误时，发送这一个 `Err` 然后就停止——不重试，也不去尝试在后面的
  字节里重新找记录边界（一段已经证明不可信的数据流里，没有可靠的办法找到下一个
  记录的起点）。双端模式下，给每个 mate 文件各起一个这样的线程，正是让 R1、R2
  能够**并发**解压而不是顺序解压的原因——跟 `docs/zh/sample.md` 里讲的是同一个
  I/O 层收益。

- **`PairStep` / `recv_pair_step(rx1, rx2)`**：从两个 mate 各自的 channel 里
  各取一条记录，把结果归成四种情况之一——`Pair { r1, r2, ids_match }`（两边都
  拿到了记录；`ids_match` 记录 `FastqRecord::base_id()` 是否一致）、`Eof`
  （两个 channel 在同一步同时关闭——干净的同步结束）、`CountMismatch`（一边关闭
  了，另一边还有数据）、`ReadError`（某一边真的遇到了读取/解析失败）。这个函数
  刻意不对"哪种情况算坏"做任何判断——完全交给调用者决定。`sample::recv_pair`
  （`src/fastx/sample.rs`）把 `CountMismatch`、`ReadError`、以及
  `ids_match` 为 false 这三种情况都通过 `bail!` 变成硬错误；`rescue::run_pe`
  把完全相同的三种情况变成"停止循环、打一条警告日志、保留已经写出去的内容"。

这跟 `fastx rename` 文档里从另一个角度讲的是同一个道理：当两个命令需要同一套
机制、但机制之上要套的策略不一样时，应该在"函数返回值"这一层把"发生了什么"
（机制）和"该怎么处理"（策略）分开，而不是给一个函数加一个
`bail_on_error: bool` 参数——因为以后每多一种调用者的策略变体，这个参数就得
再长出一个新分支。

## 什么算是"到此为止"

有三种不同的情况会让一次 rescue 提前结束，日志里会把它们区分开，方便用户（或者
解析日志的脚本）知道具体发生了什么：

1. **读取/解析错误**——gzip 流本身损坏或被截断，或者某条记录结构不完整（缺一行、
   `+` 行不是以 `+` 开头、或者序列和质量值长度对不上）。对应
   `PairStep::ReadError`，单端模式下则是 channel 直接收到的 `Err`。
2. **条数不一致**（仅双端）——某个 mate 的数据流（不管是不是正常结束）比另一个
   先结束了。哪怕较短的那个文件是"干净"结束的，一旦有一边先没数据了，就不存在
   还能保留的完整配对了。
3. **ID 不匹配**（仅双端，默认开启）——两边都拿到了记录，但
   `FastqRecord::base_id()` 对不上。这种情况本身通常**就是**损坏的真实体现：
   截断点之后的垃圾字节，纯属巧合也可能刚好解析成语法上"看起来正常"的 FASTQ
   行，哪怕四行结构本身看着没毛病，靠 base ID 比对也能把这种情况揪出来。
   `--no-pair-check` 只关掉这一项检查（`CountMismatch` 和 `ReadError` 依然会
   照常终止流程）——只有在你的 header 不遵循 `base_id()` 所依赖的 `/1`+`/2`
   或者 Illumina 风格 `1:...`+`2:...` mate 后缀约定时才应该用它。

如果从头到尾顺利跑完——两边都干净地走到 `PairStep::Eof`（或者 channel 干净
关闭），从未撞上以上任何一种情况——日志会报告"没有检测到损坏"，而不是当作一次
"拯救"；这种情况下命令实际上起到的是一个严格的透传式校验器的作用，代价也不过是
把文件完整读一遍而已。

## 退出码：让"部分拯救"能和"完全成功"、"彻底失败"区分开

一次 rescue 可能有三种性质完全不同的结果，脚本调用时很可能需要分别处理，所以
这里用了三种退出码，而不是常规的 0/1：

- **0**——从头到尾读得干干净净，什么都没损坏，什么数据都没丢。
- **3**——检测到了损坏，但至少成功拯救并写出了一条记录（或一对）。
- **1**——检测到了损坏，而且**什么都没能保住**（比如第一条记录就坏了），或者
  参数/文件本身就不对。没产出任何有用的东西。

这样脚本里就能写出类似
`if genorush fastx rescue ...; then ... elif [ $? -eq 3 ]; then echo "只拯救了部分，去看日志"; else echo "这个文件没法用"; fi`
这样有意义的分支逻辑。

### 一个坑：`std::process::exit` 不会执行析构函数（以及 `BlockWriter` 为什么绕开了它）

`rescue.rs` 里的 `finish()` 对 1/3 这两种情况直接调用了
`std::process::exit(code)`，因为 Rust 常规的 `main() -> Result<()>` 退出码
约定只能区分 0 和 1。但 `std::process::exit` 会**立即**终止进程，**不执行任何
析构函数**——这个命令第一版就正好撞上了这个坑：当时写入用的是
`io_utils::open_writer`，它的 gzip 分支是一个长期存活的单个
`flate2::write::GzEncoder`，尾部校验信息（CRC32 + 原始大小）是在它的 `Drop`
实现里才写的，不是在 `flush()` 的时候。`GzEncoder` 还活着的时候就调用
`process::exit`，产出的 `.gz` 文件会有合法的文件头和正文，但尾部缺失——任何
gzip 读取工具都会正确地判定这个文件"被截断了"，尽管拯救出来的**内容**本身
逐字节都是对的。当时的修法是在调用 `finish()` 之前显式 `drop(writer)`，强制
让编码器的尾部在正常的 Rust 作用域析构机制还生效的时候就写下去。

现在这个 workaround 已经不在代码里了——不是因为又打了个补丁绕过去，而是因为
它所针对的那个类型本身已经不用了。`rescue` 后来迁移到了
`io_utils::BlockWriter`（为什么要有这个类型见 `docs/zh/sample.md`），跟其他
分块处理的命令一样拿到了并行压缩：确认无误的记录攒够 `--chunk-records` 一批
就交给 `write_blocks`，一旦碰到损坏或者输入读完，剩下不满一批的也会立刻冲刷
写出。`BlockWriter` 的 gzip 分支是给每一块都**现建一个**`GzEncoder`，并且在
产出这个 encoder 的**同一次** `write_blocks` 调用里同步调用 `.finish()`——
所以 `write_blocks` 一返回，每个 gzip member 就已经完整了，尾部也已经写好，
不存在任何依赖 `Drop` 才会补上的、悬而未决的编码器状态，也就没有什么能被
`process::exit` 弄丢了。`writer.flush()`（`finish()` 之前依然会调用）现在
只需要把底层 `BufWriter` 缓冲区里的字节推给操作系统，是个很直白、没有风险的
操作。这条经验本身还是值得记住——把"可能提前退出的代码路径"和"把关键工作
推迟到 `Drop` 里做的东西"混在一起用是个陷阱——只是这个具体案例在这份代码库里
已经不复存在了。

## 局限性

这里只能检测**结构性**的损坏——也就是 flate2 本身或者 `read_fastq_record` 自己
的校验逻辑真的能观察到的问题（gzip 数据本身损坏、记录被截断、header/plus 行/
序列质量值长度不对）。FASTQ 格式本身不带任何逐条记录的校验和，所以那种四行结构
和长度都完好、但序列/质量值内容本身被打乱的位级损坏，对这个命令（以及对任何其他
FASTQ 工具）来说都是不可见的。

## 已验证的行为

用跟 `fastx sample` 相同的 20 万对 / 2 万条长读长合成数据集，故意做了截断测试：
把一个单端 `.fq.gz` 截到原大小的 60%，拯救出来的文件被 `gzip -t` 判定为完全
合法，内容跟原始未压缩文件对应前缀部分逐字节一致。双端场景下 R1 保持完整、R2
截到 70%，拯救出的 R1/R2 配对条数完全一致，全部输出里 ID 零错位。一个明文
（非 gzip）文件在记录中间被截断，被序列/质量值长度这条结构性检查抓到，而不是
靠解压错误抓到，证明这个检测机制不是 gzip 专用的。一个完全干净的文件原样通过，
退出码 0，没有任何数据丢失。一个从第一条记录就损坏的文件正确地以退出码 1 结束，
拯救出 0 条记录。`--no-pair-check` 验证过只会关掉 ID 检查（一份人为让 ID 错位
但条数仍然匹配的文件在这个选项下能完整读完），条数不一致的检查依然照常生效。
