# `fastx pair`：设计与实现原理

对应源码：`src/fastx/pair.rs`。

## 动机

质控会破坏配对。修剪工具因为长度不够丢掉了 R1 里的一条 read，它在 R2 里的
mate 通过了、留了下来。从这条记录往后，两个文件对"第几条是哪条 read"的理解
就不一致了——而两个文件**都仍然是完全合法的 FASTQ**，没有任何报错。下游那些
按位置配对的工具（大多数都是）于是把 read 和错误的 mate 对在了一起。

这和 `fastx deinterleave` 拒绝猜测的那类故障是同一性质，只是从另一个方向来：
不是"这条属于哪个 mate"，而是"这条还有没有 mate"。

## 为什么不把一个文件建索引

显而易见的实现是：把一个文件按 read ID 读进一个映射，再流式扫另一个。现有工具
都是这么做的，代价是内存变成**输入规模**的函数：

- `seqkit pair` 在 49 GB + 62 GB 的一对文件上被报告吃掉约 380 GB 内存后崩溃，
  当时输出才写了 400 MB（[shenwei356/seqkit#305](https://github.com/shenwei356/seqkit/issues/305)，
  至今无人回应）
- BBMap 的 `repair.sh` 需要 JVM，还要预先指定堆大小
- `fastq-pair` 小而快，但不读 gzip

真实的失步几乎从不与输入规模成正比：被过滤掉的是百分之几，其余部分的相对顺序
没有变。为了应付这点失步而付整个文件的代价，形状就不对。

## 流式连接

两个文件并发读取，各取一条、严格交替，让两边的读取位置始终停在同一个序号附近。

- mate **已经见过**的记录：立刻成对写出，两条都不保留
- mate **还没见过**的记录：进入 `pending`

于是峰值内存等于"最坏时刻还没配上的记录数"——即真实失步量加上孤儿量——而不是
文件大小。在一份 2000 条记录、两侧各缺约 1% 的数据上实测：

| 输入 | 峰值持有记录数 |
|---|---|
| 同序，两侧各缺少若干条 | 44 |
| 一侧完全逆序 | 1978（整整一侧） |
| 一侧完全逆序，8 KB 预算触发溢出 | 84 |

第一行是这个命令要服务的常态。第二行是设计必须**扛住**而不是优化掉的情况：
第一条记录的 mate 躺在另一个文件的最末尾，在读到那里之前没有任何东西可以释放。

### 输出对齐是免费的，输入顺序不是

因为一对的两条记录是在同一步写出的，R1 输出的第 `i` 条与 R2 输出的第 `i` 条
必然是一对。这个对齐不花任何代价，在所有路径上都成立——它是这个命令的全部
意义，不是拿来和内存做交换的约束。

保持**输入顺序**则是另一回事。当输入本来就同序时它自然成立，因为那时配对是按
顺序完成的；输入乱序时输出顺序是"配对完成的顺序"；走了磁盘回退之后则是分区
顺序。运行时会明确报出走的是哪一种，而不是留给用户去发现。

### 为什么不提前判定孤儿

很诱人的一个优化是：当另一条流已经走过了 mate"本该出现"的位置，就把 `pending`
里的记录刷出去当孤儿——那样内存就只和失步量成正比，不含孤儿。但这只在两个文件
同序时才成立，而"同序"恰恰是一个重新配对的工具**不能假设**的前提：被按名字
排过序、或者从无序来源重建的文件都会打破它。一条被当作孤儿刷出去、mate 却在
后面才出现的记录，就是静默的数据丢失——正是这个命令要防的那种故障。所以孤儿
只在读到 EOF、能够证明的时候才判定。

## 磁盘回退

当 `pending` 涨过 `--max-memory`，继续持有不行，猜测也不行。出路是数据库解决
同一形状问题的老办法——哈希分区连接（Grace hash join）。

两边剩余的记录各自按 `hash(read ID) % k` 写进 `--partitions` 个分区文件。一对
mate 的哈希必然相同，所以**一对记录不可能被拆到两个分区里**，于是每个分区可以
独立连接，任何时刻只需要一个分区常驻内存。峰值内存变成 `k` 的函数而不是输入的
函数；分区文件在连接过程中用完即删，所以磁盘峰值只出现在连接刚开始的那一刻。

溢出的记录用一种自有的简单编码写出——一个 `u64` 原始序号，随后四个字段各自带
长度前缀——而不是写成 FASTQ。序号必须跟着走，孤儿才能按输入顺序回来；而当
header 里什么字符都可能出现（包括制表符）时，长度前缀比分隔符可靠。

溢出文件走的是所有命令共用的 `BlockWriter`，因此是并行 gzip 压缩的；读回时走
`open_reader`，按内容识别压缩。

### 临时文件

溢出目录建在 `--temp-dir`（默认为运行目录）下，运行结束时删除，包括各条错误
路径——靠一个在作用域退出时执行的守卫完成。

目录是**先创建、再查空间**，这个顺序不是随意的。"对一个不存在的路径查可用
空间"并不是一种可移植的判断方式：POSIX 的 `statvfs` 会返回 `ENOENT`，而
Windows 会把任何语法合法的路径解析到它所在的卷根，然后老老实实回答这个卷的
空间。先把目录建出来，就在所有平台上同时回答了两个问题——它存不存在、能不能
写——而如果随后发现空间不够，守卫会把它再删掉。

可用空间的检查基准是输入文件的磁盘占用加 10%。这个估计是**偏大**的（实际只会
溢出未配对的那部分，而且压缩方式与输入相同），而偏大正是该有的方向：连接跑到
一半磁盘写满，留下的是一个没有答案的目录和一堆分区文件。

还有一处平台差异直接影响连接本身：Unix 允许删除仍被打开的文件，Windows 不允许。
分区文件是边连接边删的，所以轮到某个分区时，它上面的 writer 和 reader 必须都已
释放——`Partitions::finish` 通过消费 `self` 来释放 writer，每个读取阶段也各自
限定了作用域。

## 已验证的行为

`tests/pair_join.rs` 把同一份输入分别送进三条路径——内存内且同序、内存内但逆序、
溢出到磁盘——要求三者给出**完全相同**的配对集合与两份孤儿清单，且每次输出都
逐位置对齐。一个悄悄和快路径算出不同结果的回退，比一个干脆拒绝运行的回退更糟。

另外覆盖了：快路径不会碰磁盘、溢出目录事后确实消失、没有地方可放的孤儿仍然被
计数并报告而不是悄悄丢弃、无法使用的 `--temp-dir` 在开始溢出之前就被报出来、
以及不是尺寸的 `--max-memory` 会被拒绝而不是当成 0。
