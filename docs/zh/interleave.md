# `fastx interleave` / `fastx deinterleave`：设计与实现原理

对应源码：`src/fastx/interleave.rs`、`src/fastx/deinterleave.rs`、`src/common/hash.rs`。

## 动机

两个方向，两个完全不同的问题。把 R1/R2 合并成一个 interleaved 文件
（`fastx interleave`）没有歧义——输出格式是我们自己决定的，所以永远是规范的
`R1,R2,R1,R2,...`交替排列，这也是 `bwa mem -p` 这类工具期望的约定。把合并过的
文件拆回去（`fastx deinterleave`）才是难的方向，因为"合并过"在实际使用中根本
不是单一格式。规范的 interleaved 文件是两个 mate 交替排列的；但流通中大量文件
其实就是简单的 `cat R1.fastq R2.fastq > merged.fastq`——全部 R1 记录排在前面，
全部 R2 记录排在后面。这两种不是"同一种格式的不同外衣"：一个假设 interleaved
的拆分工具遇到 cat 拼接出来的文件，会**静默产出垃圾结果**——把两条毫不相关的
read 硬凑成"配对"，而且完全不会报错。这个问题是从真实使用场景里直接冒出来的
——`docs/zh/sample.md` 和 `docs/zh/rescue.md` 里已经吃过两次同样的教训（配对
正确性必须验证，不能假设）——`fastx deinterleave` 是这个教训在第三个地方的
应用。

## 第三种布局：位置根本不携带信息的情况

上面两种布局都是**按位置**的：一条记录属于哪个 mate，是它在文件里位置的函数。
但真实世界里存在这个前提完全不成立的文件，而且就是在拿这个命令跟它要替代的
shell 流程做对照验证时撞上的。

`SRR17458599.fastq.gz`（14.76 GB，399,065,686 条记录）的布局是：

```
第          1 …  24,174,089 条   全是 /2   （ 24,174,089 条）
第 24,174,090 … 223,706,932 条   全是 /1   （199,532,843 条）
第 223,706,933 … 399,065,686 条  全是 /2   （175,358,754 条）
```

是三段而不是两段，所以 concat 假设不成立；每段又都很长，所以 interleaved 假设
在第一对就崩了。对任何基于 ID 的推断更致命的是：整个文件的 read 编号是**全局
连续**的（实测 3.99 亿条记录里一次跳变都没有），这意味着一对 mate 拿到的是两个
**不同**的 ID——`@SRR17458599.1 1/2` 的配对读段是
`@SRR17458599.24174090 24174090/1`。`base_id()` 比较没法把这个文件配起来，
任何位置规则也拆不了它。

真正管用的，是每条记录自己携带的那一点信息：header 里的 `/1` 或 `/2` 标记。
这就是 `--layout by-suffix` 的判据，也是流通已久的那些 `awk` 一行流一直在做的
事情——

```awk
if (header ~ /\/1(\s|$)/)      print ... >> r1
else if (header ~ /\/2(\s|$)/) print ... >> r2
```

——所以在按位置拆分的工具束手无策的时候，那些流程反而能处理这类文件。

## 识别布局：先探头部，再边写边验

要验证"拼接"这个假设，必须先知道**记录总数**才能表述它——第 `i` 条记录被假设
要跟第 `i + n/2` 条对应，而在读完整个文件之前根本不知道 `n/2` 是多少。早期版本
把这一点执行得很字面：永远把输入读两遍，一遍把每条记录的 `base_id()` 哈希进
内存做判断，一遍真正拆分。在上面那个文件上，这个代价是 5 分钟加 **3.05 GiB**
常驻内存（8 字节 × 3.99 亿条），而结论仅仅是"两个假设都不成立"。

现在 `--layout auto` 改成先探测：读头部 `PROBE_RECORDS`（4096）条记录，问两个
问题：

1. **相邻记录是否共享 base id？** 如果探测范围内每一对 `(2i, 2i+1)` 都共享，
   这个文件看起来就是 interleaved。
2. **是否每条记录都带 `/1` 或 `/2` 标记？** 如果是——并且它不是 interleaved
   ——那么每条记录都能按自己的 header 分流，文件怎么排列都无所谓：`by-suffix`。

只有两个问题都答不上来（既没有标记，也没有共享 ID）时，才回退到"全量哈希"的
老路——那仍然是识别"mate 共享 ID、又不带标记的拼接文件"的唯一办法，也是现在
**唯一**一条内存随输入增长的代码路径。

探测是证据，不是证明，所以选中的拆分函数会在写出的过程中逐条复核自己的假设：
`split_interleaved` 要求每一对的两条记录共享 base id，`split_by_suffix` 要求
每条记录都带标记，`split_concat` 要求同一半内部带标记的记录彼此一致、且两半
互不相同。任何一处违反都会中止，并报出具体的记录序号，以及应该改用哪个模式。

代价是明确的：违反现在是在**已经写出一部分输出之后**才被发现，而不是在写任何
东西之前。这样的运行会以非零退出码结束，并明确说明输出文件必须丢弃。换来的是
常见情况下不再把几十 GB 的输入读两遍。"拒绝瞎猜"仍然是原则——变的只是这次
拒绝的代价从一次全量扫描降到一次头部探测，以及"记录能自证身份的文件"不再被
归进"猜不出来"这一类。

`--layout interleaved`/`--layout concat`/`--layout by-suffix` 会完全跳过探测。
`interleaved` 和 `by-suffix` 都是单遍流式、不占额外内存。`concat` 依然需要提前
知道中点，所以会先做一遍只计数的扫描——比哈希扫描便宜，但仍然是一次真实的
预扫描，因为中点位置本来就是"整个文件长度"的函数。

## 按 header 标记分流（`--layout by-suffix`）

`FastqRecord::mate_suffix()` 会扫描**整个** header，找后面跟着空白字符或者
直接就是行尾的 `/1`、`/2`，刻意对齐上面那个 `awk` 的约定。扫整个 header
（而不是像 `base_id()` 那样只看第一个 token）正是 SRA 那种布局能被处理的原因
——那里标记落在第二个字段里：`@SRR17458599.1 1/2`。

有两种写法是**刻意不当作**标记的：

- 现代 Illumina header（`@ID 1:N:0:ATCG`）。那里的 mate 编号属于另一套语法的
  字段，把它当标记会误读任何恰好含有类似字段的 header。这类 header 的文件在
  实际中都是 interleaved 或 concat 的，按位置的模式能处理。
- 标记后面粘着其他字符（`@READ/12`、`@READ/1x`）。标记必须是行尾，或者后面
  跟空白字符。

这个模式有一处**刻意比它复刻的 `awk` 更严格**：完全不带标记的记录会直接报错，
而不是往 stderr 打一行警告。shell 版本是警告一句然后丢掉这条记录——意味着在
一个跑几个小时的作业中间悄悄丢数据，最后还是退出码 0。而在一个"位置不携带任何
信息"是全部前提的模式里，对那条记录根本没有别的东西可以回退。

最后，`by-suffix` 没法像按位置拆分那样白拿一个保证：R1 和 R2 条数相同。所以
结束时会比较两边的记录数，不相等就报错——输出文件是完整写出来的，但它们不能
被下游当成"按位置配对"的一对文件来用，运行会把这一点说明白并以非零码退出。

## 为什么用哈希而不是完整 ID 字符串

下面这段针对的是上面说的那条回退检测路径——现在唯一还会按记录累积状态的路径。

`common::hash::fnv1a` 是一个很小、无外部依赖、非加密用途的哈希函数。它不是
"绝对不会碰撞"的，这是一个刻意的、写清楚的取舍：对真实的 read ID 来说（结构化、
不相关的 read 之间事实上永远不同），64 位哈希意外碰撞的概率，跟这套机制本来
要抓的真实故障模式（文件根本不是单一、干净的某种布局）相比，小到可以忽略不计。
给几亿条记录存完整 ID 字符串要多花几十 GB 内存，换不来对应的正确性收益；
`fastx cat` 的查重检查（见 `docs/zh/cat.md`）出于同样的理由复用了同一个哈希
函数。

## 拆分时不需要跟分块或中点边界对齐

三个拆分函数（`split_interleaved`、`split_concat`、`split_by_suffix`）
都是按 `--chunk-records` 大小分批处理
输入（用 `common::fastq::format_into_blocks`/`io_utils::BlockWriter` 并行
压缩，跟 `fastx sample` 用的是同一套机制——见 `docs/zh/sample.md`），但两者
都跟踪的是**全局**递增序号而不是每批重新从零计数，所以哪怕某一批数据正好跨在
奇偶边界上（interleaved）或者 `n/2` 中点上（concat），批内逐条记录依然能被
正确分流。两个拆分函数都不需要分块边界跟数据里任何有意义的位置对齐。

## `fastx interleave`：不需要检测，顺序在任意分块压缩下都保持不变

因为输出格式完全是我们自己定的，每一批缓冲的配对在交给
`format_into_blocks` 之前会被展平成 `[r1, r2, r1, r2, ...]`，
`format_into_blocks` 再把这个列表切成 `rayon::current_num_threads()` 份，
各自独立 gzip 压缩。哪怕某个分块边界正好落在一对 `r1`/`r2` 中间也完全没问题
——gzip 解压只是按顺序把所有块拼回一条连续字节流，而这条流跟展平列表本身
完全一致，压缩时怎么切块并不影响这一点。**读**这一侧的配对正确性复用的是
`spawn_reader`/`recv_pair_step`，以及跟 `fastx sample`/`fastx rescue` 相同的
`--no-pair-check` 逃生舱口。

## 已验证的行为

用三份构造出来的、各 500 对的输入做了测试：一份真正的 interleaved 文件、一份
`cat R1 R2` 风格的拼接文件、一份完全打乱（两种布局都不是）的文件。
`--layout auto` 正确识别出了前两种，对第三种拒绝瞎猜，把两个假设各自第一次
不匹配的具体位置都报了出来。两种正确识别出来的场景，拆分后的内容都验证跟原始
R1/R2 逐字节一致。`--layout interleaved`/`--layout concat`（显式指定、跳过
检测）也用同一批测试数据验证过。完整的往返测试——先 `interleave` 再
`deinterleave`——验证能精确还原出原始的 R1/R2。

单元测试直接覆盖了每个拆分函数的分流逻辑和每一道校验：正常的 interleaved
拆分、被拒绝的非配对记录、用 `--no-pair-check` 覆盖这个拒绝、concat 拆分
（包括中点落在某个分块内部的情况）、mate 分段没对齐中点因而被拒绝的 concat、
`by-suffix` 处理乱序文件并保持各 mate 内部的原始顺序、不带标记的记录被拒绝，
以及头部探测的四种结论。

之后 `by-suffix` 用上文那份真实的 `SRR17458599` 数据，与它要替代的流程做了
对照验证：

- 取 400,000 条记录的切片，分别用原始 `awk` 和 `genorush`（一次走
  `--layout auto`，一次显式 `--layout by-suffix`）拆分。三份 R1 输出逐字节
  完全一致（`cmp` 无差异，md5 均为 `881b2b54…`），三份 R2 输出同样一致
  （md5 `486db68d…`）。
- 同一份切片上，`--layout concat` 会在中点拆开并发出警告，说明 `--out1` 里
  装的其实是 R2 ——正是促使加上这道校验的那种"静默 mate 对调"。
- 随后用 `--layout auto` 把完整的 14.76 GB 文件端到端拆分了一遍（探测头部后
  自动选择了 `by-suffix`），两侧各得到 199,532,843 条记录。解压之后，两个输出
  与 `awk` 流程当初跑出来的结果 md5 完全相同：R1 为
  `01b115c750218ce9ff7746fec545d0bd`，R2 为
  `9a0643deb542c83d453176d6b419e840`。
- 这次运行在 `-j 12` 下耗时 12 分 32 秒，峰值常驻内存 **45 MiB**。作为对照，
  同一份输入在旧的"永远全量哈希"检测下，光是走到"无法判断布局"这个错误就花了
  5 分钟和 3.05 GiB，而且一条记录都还没拆。
